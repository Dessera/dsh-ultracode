# DSH 版本兼容性

[English](compatibility.md) | 中文

`@dessera/dsh-ultracode` 声明了自己支持哪些 DSH 版本。这份文档列出这些版本，说明这行声明起什么作用，说明怎样检查一个版本、怎样把一个新版本加进来，并说明这些检查能得出什么结论、不能得出什么结论。

## 支持的版本

| 序列          | 已验证版本                       | 说明                                               |
| ------------- | -------------------------------- | -------------------------------------------------- |
| `0.1.5-rc`    | `0.1.5-rc.3`                     | 支持范围里最旧的一档，类型引用也钉在这一档上。     |
| `0.1.6-alpha` | `0.1.6-alpha.1`、`0.1.6-alpha.2` | 这一序列已发布的全部版本；该档宿主不读 peer 要求。 |
| `0.1.7-rc`    | `0.1.7-rc.2`                     | 第一个其宿主真正执行 peer 检查的序列。             |

声明的范围由若干段组成，每一段对应一个序列，段与段之间用 `||` 连接。一段从该序列里已经测过的最旧版本开始，同一序列里更晚发布的版本都在覆盖之内；比这一段起点更早的版本，以及文件里没有列出的序列的版本，都会被拒绝。

## 这行声明起什么作用

范围写在 `package.json` 里：

```json
{
    "peerDependencies": {
        "@deepseek-ai/dsh": ">=0.1.5-rc.3 <0.1.6-0 || >=0.1.6-alpha.1 <0.1.7-0 || >=0.1.7-rc.2 <0.1.8-0"
    }
}
```

DSH 宿主在加载插件之前会读这个字段，并把它正在运行的版本与其中每一个 `@deepseek-ai/dsh` 或 `@deepseek-ai/dsh-*` 条目逐一比较。当运行中的版本落在范围之外时，宿主会拒绝这个插件：安装会失败并报出是哪一项对不上；已经装了这个插件的宿主会在启动时拒绝加载它。如果你看过风险之后仍然决定接受，可以用 `dsh plugin allow-version` 为「这个插件版本 + 这个宿主版本」登记一条豁免，之后宿主就会加载它。

版本号有两条规定决定上面这个范围该怎么写。

- 预发布版本的编号低于同一版本的正式发布。因此 `^0.1.5` 不包含 `0.1.5-rc.3`；一段如果要从一个预发布版本开始，就必须像 `>=0.1.5-rc.3` 这样把那个预发布版本写出来。
- 较晚版本的预发布又低于那个较晚的版本本身。因此 `<0.1.8` 包含 `0.1.8-alpha.1`；一个要排除下一个序列的上界必须加上 `-0`，写成 `<0.1.8-0` 这样。

宿主从 `0.1.7-rc.1` 这个版本起才会执行这项检查。在 `0.1.5-rc` 与 `0.1.6-alpha` 的宿主上，无论范围是否匹配，插件都会被加载，所以这行声明只对较新的宿主起保护作用。

## 这份列表从哪里来

`compat/versions.json` 记着支持的序列以及每个序列里测过的版本。有三样东西由这个文件生成，而且都不再重复写一遍版本号：

| 由该文件生成 | 出现在哪里                           | 谁来读                 |
| ------------ | ------------------------------------ | ---------------------- |
| 声明的范围   | `package.json` 的 `peerDependencies` | 宿主，在加载插件之前   |
| 版本列表     | 持续集成的各个任务                   | 每个受支持版本一项     |
| 支持表格     | 两份 README 与本文档                 | 正在决定要不要安装的人 |

有一个测试让这三者保持一致。`test/peer-range.test.mjs` 会在下面四种情况下失败：声明的范围不是由 `compat/versions.json` 生成的那个范围；这个范围拒绝了文件里列出的某个版本；这个范围接纳了比某个受支持序列里最旧的那个已列出版本还要旧的版本，或者接纳了文件没有列出的某个序列的版本；又或者某份带支持表格的文档漏掉了某个版本。

## 怎样运行这些检查

```sh
pnpm compat            # 对每一个受支持版本跑一遍测试套件
pnpm compat --type     # 另外对范围两端各做一次类型检查
pnpm compat --offline  # 只用已经缓存的副本
```

执行器会为每一个版本在缓存目录下装一份供测试使用的宿主副本（`DSH_COMPAT_CACHE`，Windows 上默认是 `%LOCALAPPDATA%\dsh-compat`，其他平台默认是 `~/.cache/dsh-compat`），把 `DSH_HOME` 指向这份副本，然后对它跑本仓库的测试套件。因此不需要有人手工安装任何一个版本。

有两个细节让结论可信。执行器会报出它实际读到的版本，因此一次运行不会悄悄检查了另一个版本。如果读到的宿主来自它安装目录之外，执行器会报错停下；因为 Node 解析一个包名时会依次到每一层父目录里去找，否则一次运行可能读到这台机器上装的那份 DSH，却为从未安装过的版本报出成功。

| 选项            | 作用                                                                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------- |
| `--version <v>` | 只对指定的这一个版本做检查。这里可以写 `compat/versions.json` 里还没有的版本，候选版本就是这么先试一遍的。       |
| `--heads`       | 另外从 npm 解析 `next` 与 `alpha` 两个标签，并对解析出来的版本做检查。它们的结果会被报告，但不会让这次运行失败。 |
| `--type`        | 另外对支持范围的两端各做一次类型检查。                                                                           |
| `--offline`     | 只用已经缓存的副本，缺任何一份就失败。                                                                           |
| `--json`        | 把报告以 JSON 写到标准输出，进度信息写到标准错误。                                                               |
| `--update`      | 把这次运行的结果写入 `compat/matrix.json`。                                                                      |
| `--list`        | 写出计划。与 `--json` 一起用时，还会写出持续集成任务要读的版本列表与范围两端。                                   |

退出码的含义是：每个受支持版本都通过时为 `0`；某个受支持版本或某次类型检查失败时为 `1`；执行器无法开始工作时为 `2`。

## 加入一个更新的版本

1. **先试候选版本，不要先改任何文件。** 执行器可以安装并测试一个 `compat/versions.json` 里还没有的版本，报告里会把它标成 `unlisted`：

    ```sh
    pnpm compat --version 0.1.8-rc.1
    ```

    通过意味着这个插件的各项约定与它自己的测试套件在那个版本上都成立。失败意味着上游有东西变了，见下面的「检查失败时怎么办」。

2. **确认该版本的宿主包齐备。** 这份副本是按精确版本安装的，只要有一个包在那个版本上没有发布过，整次安装就装不下去。遇到这种情况时执行器会报出缺的是哪个包。

3. **把这个版本写进 `compat/versions.json`。** 已经列出的序列，就把版本加进该序列的 `versions` 数组，由旧到新排列。新的序列则是在 `series` 里再加一项，名字用它数字部分：

    ```json
    { "name": "0.1.8-rc", "versions": ["0.1.8-rc.1"], "blocking": true }
    ```

    这一项的名字与其中的版本号必须共用同一个数字部分；不满足这一点的项在读取该文件时会被拒绝。

4. **重写 `package.json` 里声明的范围。** 生成器会把该写的字符串原样打印出来：

    ```sh
    node -e "import('./compat/plan.mjs').then(m=>console.log(m.peerRangeOf(m.readPlan().series)))"
    ```

    如果跳过这一步，第 6 步会给出同一个字符串：`pnpm check` 会失败，并把期望的范围报出来。

5. **把新版本号加进两份 README 与本文档的表格。**

6. **先跑 `pnpm compat`，再跑 `pnpm check`。** 持续集成的各个任务、类型检查、以及门禁所用的宿主版本都跟随 `compat/versions.json`，因此它们都不需要改。

7. **发布一个版本。** 宿主依据的是已安装包里的那行声明，所以要等这个包的新版本发布出去之后，用户那边的支持范围才会改变。

## 抬高最旧的受支持版本

`devDependencies` 里的类型引用钉在最旧的受支持版本上，正因为如此，编译器会拒绝这个版本没有发布的任何 API。因此放弃这个版本时，类型引用也要跟着动：

1. 把 `devDependencies` 里每一个 `@deepseek-ai/dsh*` 指向新的最旧版本，然后运行 `pnpm install`。
2. 运行 `pnpm compat --type`。如果失败，说明源码用到了新的最旧版本没有发布的某个 API。把代码改成两个版本都能用的写法，或者维持现有的支持范围不变。
3. 接着按上一节的步骤做，因为序列列表也变了。

## 在某台机器上把 DSH 升级

这是在机器上做的动作，不是在仓库里做的。把 DSH 安装升级、重启宿主即可，插件加载时就会检查那行声明。版本落在范围之外的宿主会拒绝这个插件，可以用 `dsh plugin allow-version` 为那台机器登记一条豁免。另一条路是在这里支持那个版本并发布一个版本，也就是「加入一个更新的版本」那一节的流程。

## 检查失败时怎么办

- **契约探针报出某个名字不见了。** 插件用到的某个服务键、座位名、座位属性、日志事件或浏览器名字，在上游已经不再叫这个名字。要么把插件改成新旧两个名字都能用，要么不再声称支持那个版本。
- **类型检查失败。** 某个类型声明在最旧与最新的受支持版本之间变了。如果源码能写成两个版本都适用的样子，范围可以保持不变；如果写不出来，范围就得收窄。
- **文档测试失败。** 某张表没有更新，或者声明的范围是手工改的而不是生成的。
- **某个版本的副本装不起来。** 要么那个版本没有发布探针要读的每一个包，要么 npm 不接受待安装的这些包所声明的 peer 要求。执行器会报出遇到的是哪一种。

## 这些检查能得出什么结论

这些检查能得出两个结论。第一，插件用到的每一个服务、座位、事件与浏览器名字，在每一个受支持版本上仍然叫这个名字。第二，源码对最旧与最新的受支持版本的类型声明都仍然编译得过。

这些检查得不出「一个名字仍然指同一件事」这个结论。举例来说，如果将来的宿主仍然保留某个服务的名字，却改变了它某个方法的作用，本仓库里的每一项检查都会通过，而这个插件在会话里仍然可能出错。要发现这类变化，只能真的在一次会话里用这个插件。类型检查比只知道名字的检查多验一层，因为它还会拿插件的代码与声明的类型比对，但它只覆盖范围两端的那两个版本。
